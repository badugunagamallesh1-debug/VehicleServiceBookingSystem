4. ABSTRACT & KEYWORDS
================================================================================
ABSTRACT:
The Vehicle Service Booking System (VehiXPro) is an enterprise-grade full-stack web application engineered to transform automotive repair and maintenance workflows. Operating as a multi-tenant platform, it connects Customers, Certified Mechanics, and System Administrators through a real-time digital interface.

Built using React 19, TypeScript 5, Express.js, Tailwind CSS, and Vite, the platform integrates state-of-the-art Generative AI capabilities powered by Google Gemini. Key AI capabilities include multilingual customer support chatbots (English, Hindi, Telugu), predictive vehicle health scoring based on telemetry/mileage analysis, NLP review sentiment classification, fraud detection, and revenue forecasting.

The platform provides a step-by-step booking wizard with Google Maps Platform integration for location-based service center discovery and valet pickup tracking, a digital vehicle garage, multi-gateway payments (Razorpay, UPI), real-time notification engine, customer loyalty programs, document vault reminders, fuel expense tracking, mechanic job execution terminals, and administrative business intelligence dashboards powered by Recharts.

KEYWORDS:
Vehicle Service Booking System, React 19, TypeScript 5, Express.js, Google Maps API, Google Gemini AI, Predictive Maintenance, Full-Stack Web Application, RESTful API, Role-Based Access Control, Real-Time Notifications, Razorpay, UPI, Recharts.

6. CHAPTER 1: INTRODUCTION
================================================================================
1.1 Project Overview
The Vehicle Service Booking System (VehiXPro) digitizes the end-to-end lifecycle of vehicle servicing. It allows vehicle owners to select services, choose service centers near their location, pick convenient appointment times, request valet pickup, track repairs in real-time, and make digital payments.

1.2 Problem Statement
Traditional automotive service operations rely on phone calls, walk-ins, and manual record keeping, creating severe friction:
1. Double Bookings & Disorganized Schedules: Service centers struggle with capacity management.
2. Opaque Spare Parts Pricing: Customers lack itemized billing clarity before repairs begin.
3. Lack of Real-Time Status Visibility: Customers must repeatedly call centers to ask about vehicle progress.
4. Reactive Maintenance Model: Services occur after mechanical breakdown rather than proactively based on wear analysis.
5. Administrative Overhead: Manual payment reconciliation and paper invoice management slow operations down.

1.3 Proposed Solution
The digital solution addresses all existing pain points:
- Guided 5-Step Booking Wizard with real-time center discovery via Google Maps.
- Itemized Pricing Transparency showing package costs, pickup fees, and spare parts breakdown.
- Real-Time Notification Engine pushing status alerts at every service transition.
- AI-Driven Predictive Maintenance analyzing mileage and vehicle age to generate health scores (0-100) and recommend spare parts.
- Dedicated Mechanic Terminal for logging repair notes, attaching spare parts used, and updating vehicle states.
- Admin Operations Dashboard for mechanic dispatching, UPI payment approvals, inventory tracking, and revenue forecasting.

1.4 Objectives of the Project
1. Build a full-stack single-page application using React 19, TypeScript 5, and Express.js.
2. Enforce strict role-based access control (RBAC) across Customer, Mechanic, and Admin personas.
3. Integrate Google Maps JS API for location mapping and valet pickup vector rendering.
4. Integrate Google Gemini AI for multilingual chatbot assistance, predictive health scoring, and review fraud detection.
5. Implement over 40 RESTful API endpoints following standard HTTP methods and status codes.
6. Provide dual payment gateway workflows (Razorpay and UPI UTR approval).
7. Implement an administrative analytics dashboard using Recharts for visual reporting.

1.5 Scope of the Work
In-Scope: Web application frontend & backend, database schema, REST APIs, AI features with fallbacks, Google Maps integration, payment workflows, notifications, loyalty system, expense tracker, document vault, inventory management.
Out-of-Scope: Native mobile apps (iOS/Android), direct OBD-II hardware Bluetooth pairing, physical tow truck dispatching.

2.1 Existing Systems Overview
1. GoMechanic: Offers standardized servicing with fixed packages and pickup options. Lacks AI predictive health scoring and multilingual AI chatbot support.
2. AutoMD: Provides repair cost estimation and diagnostic lookup, but lacks online booking and real-time tracking.
3. RepairPal: Connects users with certified repair shops and provides price estimates. Lacks integrated payment portals, document vault tools, and mechanic management terminals.

8. CHAPTER 3: SYSTEM REQUIREMENTS SPECIFICATION
================================================================================
3.1 Functional Requirements
FR-01: User Authentication - System shall support registration and login for Customer, Mechanic, and Admin roles using JWT tokens.
FR-02: Digital Garage - Customers shall manage vehicle profiles (Make, Model, Year, License Plate, Type).
FR-03: Center Discovery - System shall render service centers on Google Maps with ratings, contact info, and branches.
FR-04: Booking Wizard - Customers shall complete a 5-step booking wizard with package selection and time scheduling.
FR-05: Booking Status Engine - System shall support 9 status stages (PENDING -> CONFIRMED -> VEHICLE_RECEIVED -> INSPECTION -> SERVICE_IN_PROGRESS -> WAITING_FOR_SPARE_PARTS -> QUALITY_CHECK -> READY_FOR_DELIVERY -> COMPLETED).
FR-06: Payment Gateway - System shall process Razorpay card payments and manual UPI UTR verification.
FR-07: Real-Time Alerts - System shall deliver instant in-app notification alerts for booking events.
FR-08: AI Engine - System shall query Google Gemini for Chatbot, Diagnostics, Review Analysis, and Demand Forecasting.
FR-09: Admin Dashboard - Admins shall dispatch mechanics, verify UPI payments, track inventory, and view Recharts graphs.

3.2 Non-Functional Requirements
- Performance: API response time < 500ms; Lighthouse UI score > 80.
- Scalability: Stateless Express architecture containerized with Docker.
- Availability: 99.5% operational uptime with automatic AI fallback rules.
- Usability: Fully responsive layout supporting viewports from 320px to 4K displays.
- Security: Password salting/hashing via BCrypt; JWT token verification on secured routes.

9. CHAPTER 4: SYSTEM ARCHITECTURE AND DESIGN
================================================================================
4.1 High-Level Architecture Overview
The system follows a classic 3-tier architecture:
1. Presentation Tier: Single-Page Application (SPA) built with React 19, TypeScript, Tailwind CSS, Recharts, and Google Maps JS SDK.
2. Application Tier: Node.js / Express.js REST API providing business logic, authentication filters, notification dispatchers, and Gemini AI integration.
3. Data Tier: MySQL 8.0 relational database for transactional storage, supported by Redis cache for state management (In-memory seed store used during development).

4.2 Three-Tier Layered Architecture
[ Presentation Layer: React 19 SPA ]
          │  HTTPS / REST APIs (JSON)
          ▼
[ Application Layer: Express.js API + Gemini AI SDK ]
          │  SQL Queries / Cache Lookups
          ▼
[ Data Layer: MySQL 8.0 Transactional DB + Redis Cache ]

4.3 Data Flow Diagrams
Level-0 DFD (Context Diagram):
Customer/Mechanic/Admin <---> [ Vehicle Service Booking System ] <---> External Services (Google Gemini AI, Google Maps, Razorpay)

Level-1 DFD:
[Users] -> Auth Process -> Token -> [Vehicle Garage Process] -> [Booking Engine] -> [Payment Engine] -> [Admin Operations]

4.4 UML Use Case & Sequence Diagrams
Use Cases:
- Customer: Register, Add Vehicle, Discover Centers, Book Service, Track Status, Make Payment, Chat with AI, View Health Score, Manage Vault & Expenses.
- Mechanic: View Assigned Jobs, Transition Status, Add Repair Notes, Log Spare Parts Used.
- Admin: View Analytics, Assign Mechanic, Approve/Reject UPI UTR, Manage Inventory, Generate Demand Forecasts.

11. CHAPTER 6: DATABASE DESIGN AND ENTITY RELATIONSHIPS
================================================================================
6.1 Entity-Relationship (ER) Overview
The schema consists of 14 normalized entities in 3rd Normal Form (3NF):
1. users (id, email, name, role, phone, password_hash, avatar_url)
2. roles (id, role_name)
3. vehicles (id, user_id, make, model, year, license_plate, type)
4. service_centers (id, name, address, latitude, longitude, rating, reviews_count, contact_number, image)
5. mechanics (id, user_id, center_id, availability_status)
6. services (id, name, description, price, estimated_time, features)
7. bookings (id, customer_id, customer_name, vehicle_id, vehicle_details, service_center_id, service_center_name, package_id, package_name, package_price, booking_date, booking_time, pickup_requested, pickup_location, pickup_charge, status, mechanic_id, mechanic_name, repair_notes, spare_parts_used, payment_status, payment_method, upi_utr, total_amount, invoice_id, created_at)
8. payments (id, booking_id, amount, status, method, transaction_id)
9. invoices (id, booking_id, date, total_amount, file_path)
10. reviews (id, customer_id, customer_name, service_center_id, rating, comment, date, sentiment, is_fake)
11. notifications (id, user_id, title, message, date, read_status)
12. service_history (id, vehicle_id, booking_id, completed_date, notes)
13. spare_parts (id, name, stock, price, min_stock, category)
14. pickup_requests (id, booking_id, address, latitude, longitude)
